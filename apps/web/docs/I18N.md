# Traductions — `i18n/`

L’interface existe en **anglais** et en **français**. Aucun texte affiché n’est écrit en dur dans le code : il vient d’un fichier de traduction, via `t('…')`.

Bibliothèque : [i18next](https://www.i18next.com/) + [react-i18next](https://react.i18next.com/). Pourquoi ce choix : [ADR 0012](../../../docs/adr/0012-i18n-i18next.md).

---

## Où sont les textes

Un fichier **par langue et par écran** (un « namespace ») :

```text
src/i18n/
  index.ts            instance i18next ; charge tous les fichiers ci-dessous
  i18next.d.ts        types : les clés viennent des fichiers anglais
  locales.test.ts     vérifie que fr a les mêmes fichiers et les mêmes clés que en
  locales/
    en/
      common.json     partagé par tous les écrans ("Try again", "Loading…", pied de page)
      errors.json     erreurs transverses + signIn.<code>, password.<code>, account.<code> (codes de l’API)
      header.json     AppHeader et PublicHeader (liens, menu du compte)
      auth.json       /login, /signup, /verify-email, /forgot-password, /reset-password
      settings.json   /settings (réglages du compte)
      home.json       page d’accueil publique (/)
      legal.json      /legal (mentions légales)
      wish.json       /wish
    fr/
      (mêmes fichiers, mêmes clés)
```

Un écran = un namespace. Ce qui sert à plusieurs écrans va dans `common` ou `errors`. Chaque story ne touche que ses fichiers : pas de conflits de merge sur un fichier géant.

## Ajouter un texte

1. Ajouter la clé dans le fichier **anglais** de l’écran, puis dans le fichier **français** :

   ```json
   // locales/en/auth.json
   { "forgotPassword": "Forgot your password?" }
   ```

   ```json
   // locales/fr/auth.json
   { "forgotPassword": "Mot de passe oublié ?" }
   ```

2. L’afficher :

   ```tsx
   import { useTranslation } from 'react-i18next'

   const { t } = useTranslation('auth')
   <a href="/forgot-password">{t('forgotPassword')}</a>
   ```

   Sans argument, `useTranslation()` lit `common`. Pour lire un autre namespace dans le même composant :

   ```tsx
   const { t: tErrors } = useTranslation('errors')
   ```

Une clé qui n’existe pas dans le fichier anglais est une **erreur TypeScript** (`pnpm typecheck`). Une clé oubliée dans le fichier français fait **échouer les tests** (`locales.test.ts`), avec le nom de la clé.

## Ajouter un écran (un namespace)

1. Créer `locales/en/<écran>.json` et `locales/fr/<écran>.json`, avec les mêmes clés.
2. Le déclarer dans `i18next.d.ts` (un `import type` et une ligne dans `resources`).

`index.ts` n’a pas à changer : il charge tous les fichiers de `locales/*/*.json`.

## Règles

- **Clés en camelCase**, nommées d’après ce qu’elles disent (`continueWithGoogle`), pas d’après leur place (`button1`).
- Exception : `errors.json` → `signIn.<code>` reprend **le code exact** que l’API met dans `/login?error=<code>` (`oauth_cancelled`…).
- **Variables** avec `{{nom}}`. Ne jamais construire une phrase par concaténation : l’ordre des mots change d’une langue à l’autre.

  ```json
  { "greeting": "Hello {{name}}" }          // en
  { "greeting": "Bonjour {{name}}" }        // fr
  ```
  ```tsx
  t('greeting', { name: user.name })
  ```

- **Nom de l’agence** avec `{{agency}}`, sans le passer à `t()` : `i18n/index.ts` le lit dans `brand/agency.json` (DÉTOUR). Ne jamais écrire « Novoya » dans un texte affiché au client : Novoya est le nom du projet et de l’équipe, pas celui de l’agence.

- **Pluriel** avec les suffixes `_one` / `_other`, et la variable `count` :

  ```json
  { "days_one": "{{count}} day", "days_other": "{{count}} days" }        // en
  { "days_one": "{{count}} jour", "days_other": "{{count}} jours" }      // fr
  ```
  ```tsx
  t('days', { count: 3 })
  ```

  En français, 0 et 1 prennent le singulier (`_one`) : i18next suit `Intl.PluralRules`.

- **Le français est au vouvoiement** (« Décrivez votre voyage », « Veuillez réessayer »).
- **Pas de libellé dans `domain/`.** Le domaine renvoie une **clé**, la page la traduit. Exemple : `signInErrorKey(code)` renvoie `signIn.oauth_cancelled`, et `login.tsx` affiche `tErrors(errorKey)`. Exception : `domain/agency` lit des **faits** (nom, e-mail, numéros). On ne les traduit pas. Les étiquettes (« Mentions légales », « Éditeur ») sont dans `legal.json`.
- **Les textes qui viennent de l’API ou du LLM** (destination non couverte, plan…) ne passent pas par ces fichiers : l’API les produit déjà dans la langue de l’utilisateur.
- Les composants (`components/`) peuvent appeler `useTranslation` : un texte relève de la présentation, comme `hooks/ui/`.

## Quelle langue est affichée

`resolveLocale()` dans `domain/i18n/locale.ts`, même règle que l’API (`Locale.from_hint`) :

1. connecté → `locale` de l’utilisateur (`GET /me`) ;
2. sinon → la langue choisie avec le sélecteur sur ce navigateur (`localStorage`, `i18n/storedLocale.ts`) ;
3. sinon → la **première** langue du navigateur : `fr` si elle commence par `fr` ;
4. sinon → anglais.

Au démarrage, c’est la langue du navigateur. Quand la garde `_authenticated` a chargé `/me`, `routes/__root.tsx` passe dans la langue de l’utilisateur ; après la déconnexion, on revient à celle du navigateur. `<html lang>` suit à chaque changement.

Le sélecteur EN / FR (`LanguageChoice`) est dans l’en-tête des pages connectées et dans le pied de page public. Connecté, il enregistre la langue avec `PATCH /me` avant de changer l’interface ; déconnecté, il change l’interface tout de suite. Dans les deux cas, ce navigateur s’en souvient.

Les textes des clients (avis, titre et conditions des offres) restent tels qu’écrits, en français : ils portent `lang="fr"`, et une petite note (« Review in French ») les signale quand l’interface est en anglais.

## Tests

`test/setup.ts` remet l’anglais après chaque test : les tests vérifient les textes anglais. Pour tester une autre langue, changer la `locale` de l’utilisateur simulé, ou la langue du navigateur :

```ts
vi.spyOn(navigator, 'languages', 'get').mockReturnValue(['fr-FR'])
```
