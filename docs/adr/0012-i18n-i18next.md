# 0012. i18next for the web app's translations, one file per language and screen

- **Status:** Proposed
- **Date:** 2026-10-19
- **Issue / PR:** #79

## Context

Several stories must work in English and French (#27, #31, #50, #54, #62, #45). The API
already stores the user's `locale` (`en` or `fr`), sends emails in it and will render the
quote PDF in it; `GET /me` returns it. The web app had no translation setup, and its texts
were hard-coded, some in English and some in French. Several people add screens in the same
sprint, so the translations must not all live in one file everyone edits.

## Decision

We use i18next with react-i18next in `apps/web`.

- One file per language and screen: `src/i18n/locales/<language>/<screen>.json` (i18next
  namespaces), plus `common` and `errors` for shared texts. All files are bundled.
- The English files are the reference. Their types make `t()` refuse an unknown key, and a
  test checks that every French file has exactly the same keys.
- The language is the signed-in user's `locale`, else the browser's first language (`fr` if
  it starts with `fr`), else English: the same rule as the API's `Locale.from_hint`
  (`domain/i18n/locale.ts`).
- French uses "vous". `domain/` holds no text: it returns keys, and pages translate them.
- Components may call `useTranslation`.

How to add a text: [apps/web/docs/I18N.md](../../apps/web/docs/I18N.md).

## Options considered

- **Paraglide JS:** compiled and very small, but one more code generator next to `gen:api`
  and `gen:routes`, and less known by the team.
- **Lingui:** extracts texts from the code, but needs a Babel or SWC plugin in Vite.
- **react-intl (FormatJS):** ICU messages, but a more verbose API and no typed keys out of
  the box.
- **One file per language** (`en.json`, `fr.json`): simplest, but every story would edit the
  same two files and conflict.

## Consequences

- A new screen adds `en/<screen>.json` and `fr/<screen>.json`, and one line in
  `src/i18n/i18next.d.ts`.
- `pnpm typecheck` catches a wrong key; `src/i18n/locales.test.ts` catches a missing French
  text.
- Texts made by the API or the LLM are not translated by the web app: they come in the
  user's language.
- An EN/FR switch sits in the signed-in header and the public footer: signed in, it saves
  `locale` with `PATCH /me`; signed out, this browser remembers it (localStorage), and
  `resolveLocale` prefers it to the browser's languages. Client data (reviews, the partners'
  offer texts) is shown as written, in French, with `lang="fr"` and a short "in French" note
  when the interface is in English.
- Dates and amounts will need `Intl` formatting in the user's language (quote stories).
- If the texts grow a lot, namespaces can be loaded per page later without moving files.
